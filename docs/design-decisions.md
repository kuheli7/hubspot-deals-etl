# Design decisions and trade-offs

The main choices in this service, what each one costs, and what would change for production.

| # | Decision | Why | Trade-off accepted | Production follow-up |
|---|---|---|---|---|
| 1 | **Flask-RESTX instead of Django / DRF** (confirmed acceptable by the project manager) | The assignment requires the Glynac DLT Generator, which produces a Flask-RESTX service with SQLAlchemy models and Swagger. dlt manages the deal tables, so a Django ORM would be a second data layer next to SQLAlchemy and dlt. | No Django admin or Django migrations. The job tables are created with SQLAlchemy `create_all`, and dlt evolves the deal schema itself. | Add Alembic migrations for `jobs` and `job_checkpoints`. |
| 2 | **Local HubSpot API mock** for all recorded tests | HubSpot developer sign-up required government-ID verification. The manager approved a mock that matches HubSpot's REST endpoints. | Behaviour is verified against HubSpot docs and one live 401 response, not a live account with deals. Modelled behaviour is listed separately in `mock_hubspot/README.md`. | Run `scripts/run_extraction_test.py` once against a real private app token. |
| 3 | **List endpoint (`GET /crm/v3/objects/deals`) instead of the Search API** | Returns every deal with cursor pagination and rate-limit headers, with no search result cap. | Every scan is a full extraction; there is no "changed since last run" filter. | Add an incremental mode using search on `hs_lastmodifieddate`. |
| 4 | **Checkpoint only after a batch is loaded** (one `pipeline.run` per N pages) | A checkpoint can never point past data that isn't in PostgreSQL, so pause, crash and failure all resume without gaps. | Several smaller dlt loads instead of one large one; slightly slower on very large accounts. | Tune `HUBSPOT_CHECKPOINT_INTERVAL_PAGES` (default 10 pages = 1,000 deals per load). |
| 5 | **`merge` on `id`** instead of `replace` or `append` | Re-reading a page after a resume is harmless, and re-running a scan updates rows instead of duplicating them. | dlt merges through a staging schema (delete-insert), which is slower than a plain append. Each row keeps the ID of the scan that last wrote it. | Keep a history table if every scan's snapshot must be preserved. |
| 6 | **Schema per tenant, plus `_tenant_id` on every row** | Strong isolation, simple off-boarding (`DROP SCHEMA`), and no cross-tenant leaks in queries. | Many schemas with many tenants. Cross-tenant reporting needs views or `UNION`s. | Add row-level security or per-tenant roles (see `database-schema.md`). |
| 7 | **28 typed columns plus text for extra properties**, instead of one JSON blob | Correct types (`numeric(18,2)`, `timestamptz`, `boolean`), indexes on stage and dates, and plain SQL reporting. | Making a new property strongly typed needs a code change. Until then it is stored as text. | Generate the type hints from `GET /crm/v3/properties/deals`. |
| 8 | **Job created synchronously in `POST /scan/start`**, then extraction in the background | The caller gets the `scanId` at once, and duplicate or concurrent starts are rejected atomically (409). The template's background creation could mark the first job failed. | One database write before the `202` response (milliseconds). | - |
| 9 | **In-process thread pool for scans** (as in the template) instead of a task queue | No extra infrastructure. Crashes are covered by heartbeats, crash detection and resume. | Scans stop if the process dies (then resumed manually). Throughput is limited to 4 concurrent scans per instance. | Move execution to Celery or RQ on the Redis that is already in `docker-compose.yml`. |
| 10 | **Token sent per scan request, Fernet-encrypted at rest, redacted everywhere** | Multi-tenant: each tenant uses its own HubSpot token, and paused or crashed scans can still resume. | Key management for `CONFIG_PASSWORD`. Rotating it makes stored tokens unreadable, so in-flight scans must be restarted. | Use a secrets manager or KMS. |
| 11 | **Client rate limiter at 150 requests / 10 s** (the assignment's figure) plus header-driven back-off | Stays within limits without knowing the account tier: the `X-HubSpot-RateLimit-Remaining` guard adapts to 100 (Free) or 190 (Professional). | Slightly conservative on higher tiers. | Set `HUBSPOT_RATE_LIMIT_MAX_REQUESTS` per tier. |
| 12 | **Guideline paths served as aliases** (`/scan/status/{id}`, `/jobs/jobs`, ...) | Matches TEST-GUIDELINES-V1 without breaking the generated template's documented routes. | Two URLs per operation. Swagger lists both. | Deprecate one set once clients agree. |
